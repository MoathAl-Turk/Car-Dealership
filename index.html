Car Dealership Software Architecture

A comprehensive object-oriented design project developed at Princess Sumaya University for Technology[cite: 1].

Team: Moath Al-Turk, Ehab Alhattab, Mohammad Abu Nahleh, Abdelrahman Qawaqzeh, Hamzeh Naji[cite: 1]

1. System Architecture & UML Design

The core of this project was designing a scalable system using strict object-oriented concepts to manage car manufacturing, options, ordering, and customer notifications.

2. Applied Design Patterns

  • Factory Pattern: Implemented inside the CarFactory class to handle car creation[cite: 1]. This ensures that adding new brands (like Volvo) remains isolated and does not break the rest of the purchasing flow[cite: 1].
  • Decorator Pattern: Utilized the abstract CarOptionDecorator class to dynamically add functionality (like Heated Seats or Camera360) to a car object[cite: 1]. This accumulates the total price through default attributes without altering the base structure[cite: 1].
  • Strategy Pattern: Designed the PaymentStrategy interface, implemented by CashPayment and CreditCardPayment, to accept interchangeable transaction closure methods[cite: 1]. Because Order aggregates this interface, new payment algorithms can be added without modifying the Order class[cite: 1].
  • Observer Pattern: Created an OfferPublisher to track registered subscribers and push alerts to a generic Observer interface[cite: 1]. This keeps the publisher loosely coupled, avoiding a direct reliance on the Customer class[cite: 1].

3. SOLID Principles Applied

  • Single Responsibility Principle (SRP): Every class does one specific job; for example, Customer holds data, Order calculates totals, and CarFactory creates cars[cite: 1]. Price logic is never mixed into the Customer class[cite: 1].
  • Open/Closed Principle (OCP): The architecture is open for extension but safely closed to modification[cite: 1]. Adding new decorators or payment options simply requires registering a new subclass rather than editing existing code[cite: 1].
  • Liskov Substitution Principle (LSP): Any Car subclass, including a decorated one, works seamlessly anywhere a Car is expected, allowing the Order computation engine to reliably process a car wrapped in multiple options[cite: 1].
  • Interface Segregation Principle (ISP): Small, focused interfaces (PaymentStrategy and Observer) ensure that classes like Customer are never forced to depend on interfaces or implement methods they do not use[cite: 1].
  • Dependency Inversion Principle (DIP): High-level classes depend on abstractions rather than concrete implementations[cite: 1]. The Order class depends on the Car and PaymentStrategy abstractions, not on concrete classes like BMWCar or CreditCardPayment[cite: 1].

4. Human vs. AI Architecture Comparison

As part of the engineering analysis, we generated a secondary UML model using an AI tool to evaluate structural convergence and architectural trade-offs[cite: 1].

While both designs organically converged on the exact same four design patterns, key differences emerged in tax handling[cite: 1]. Our team utilized a constant TAX_RATE inside the Order class, whereas the AI isolated the tax logic into a separate TaxCalculator class[cite: 1]. This highlights the architectural trade-off between strict adherence to the Single Responsibility Principle and the risk of over-engineering simple computations[cite: 1].
